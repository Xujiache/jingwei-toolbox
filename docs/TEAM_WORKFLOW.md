# 两人开发分工与工作流

## 1. 推荐分工

采用“后端平台”和“客户端与运营端”两条主线，接口契约由双方共同评审：

| 角色 | 主责 | 交付物 |
|---|---|---|
| 开发者 A：后端负责人 | Java + Spring Boot、MySQL 8、认证、工具注册、策略、额度、审计、OpenAPI | API、迁移脚本、服务端测试、OpenAPI 更新、运行说明 |
| 开发者 B：客户端与管理后台负责人 | HarmonyOS ArkTS/ArkUI 客户端、Vue 3 管理后台、接口接入、错误和状态展示 | 页面、网络层、类型/请求封装、后台配置页面、客户端测试 |

这种分配比“一个人只做页面、另一个人只做接口”更完整：开发者 B 同时负责两个调用方，能在同一处保证客户端和后台对接口的使用一致；开发者 A 对服务端安全、数据一致性和额度扣减负责。

## 2. 共同责任

- 双方共同评审 `docs/api/openapi.json`，任何一方不得私自改变公开字段。
- 双方共同确认工具输入输出、错误码、认证要求和游客额度。
- 双方各自对自己的分支负责，但不得合并未通过对方接口检查的 PR。
- 用户/产品决策由项目负责人确认；未确认的业务不能用临时实现冒充完成。

## 3. 分支和 PR

```text
main       生产/可发布，只接受 PR
develop    集成分支
feature/*  新功能
fix/*      缺陷修复
release/*  发布准备
hotfix/*   紧急修复
```

推荐分支示例：

```text
feature/backend-auth
feature/tool-policy-api
feature/harmonyos-tool-shell
feature/admin-tool-policy
```

规则：

1. 每个 PR 只解决一个主题。
2. 后端接口变更必须同时提交 OpenAPI、服务端测试和兼容说明。
3. 客户端或后台接入接口时必须引用接口路径、请求示例、响应示例和错误处理。
4. PR 描述必须包含：目标、影响文件、接口/数据库变化、验证命令、回滚方式、未验证内容。
5. 不直接在 `main` 上开发，不绕过审查强推公共分支。

## 4. 接口对齐流程

### 新接口

1. 开发者 A 在 `docs/api/openapi.json` 增加路径、Schema、状态码和认证要求。
2. 双方评审字段名称、可空性、枚举、分页、错误码和幂等要求。
3. 开发者 A 实现 Spring Boot 接口和服务端测试。
4. 开发者 B 根据 OpenAPI 生成或手工维护类型与请求封装，不自行发明字段。
5. 双方使用同一请求样例完成集成验证。

### 接口变更

- 兼容变更：新增可选字段、增加不影响旧客户端的枚举处理，并同步文档。
- 不兼容变更：必须增加 API/工具版本，提供迁移窗口，禁止静默覆盖旧语义。
- 删除字段、改变类型、改变错误码含义、改变额度计算方式均视为不兼容变更。

## 5. 每周交接内容

每个工作周期至少交接以下内容：

- 已完成和未完成的接口列表
- 可运行的请求示例和测试账号/测试数据说明（不得使用真实凭据）
- 数据库迁移编号和回滚命令
- 客户端/后台当前依赖的 API 版本
- 已知问题、阻塞点和下一步责任人

## 6. 合并前检查清单

### 开发者 A

- [ ] OpenAPI 与实际 Controller/DTO 一致
- [ ] 权限在服务端校验
- [ ] 游客额度有并发和幂等测试
- [ ] MySQL 迁移可执行且有回滚说明
- [ ] 错误响应不泄露敏感数据

### 开发者 B

- [ ] 请求路径、方法、字段和枚举来自 OpenAPI
- [ ] 未登录、登录、权限拒绝、额度耗尽和网络失败均有界面状态
- [ ] 不把权限判断只放在前端
- [ ] HarmonyOS 和后台构建/类型检查通过
- [ ] 未把环境变量、Token 或本地数据提交到 Git

### 双方

- [ ] 通过目标分支基线测试
- [ ] 复查 Git diff 和未跟踪文件
- [ ] 更新本目录文档和变更记录
- [ ] 明确未验证内容和回滚方式
